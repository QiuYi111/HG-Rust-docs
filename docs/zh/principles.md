# 核心哲学

HG-Rust 的设计从一个简单问题出发：自动化系统不只要“做过”，还要能说明“做出的结果为什么可信”。因此，执行、结果、版本和证据被放在同一个协调模型里。

## 1. 结果优先，而不是命令优先

Rule 不是一段孤立的脚本，而是从输入 Slot 到输出 Slot 的声明。用户首先描述想要的结果，系统再判断哪些 Rule 需要执行。

这让流程从“按顺序运行一串命令”转为“把目标协调到稳定状态”。当目标已经满足时，运行本身可以是空操作；空操作仍然有明确的 `NO_CHANGE` 证据。

## 2. 不可变版本优于“最新文件”

路径上的文件是物化结果，Revision 才是可比较、可追溯的状态。每次接受的结果都会形成新的 Revision，旧 Revision 保留在历史中。

这样可以区分三个经常被混淆的事实：

- 结果是否曾经成功产生；
- 当前 Head 指向哪个结果；
- 工作区文件是否仍与 Head 一致。

## 3. 证据优于存在性

“输出文件存在”不能证明它仍然有效。HG-Rust 使用 Receipt 记录一次 Activation 的输入、规则合约、验证结果和输出。只有 Receipt 仍然匹配当前输入与规则，才可安全复用。

## 4. 副作用必须显式化

生成文件是可版本化的结果；发送消息、修改远程资源等外部动作则是 Effect。Effect 需要幂等键，并可以通过 readback 记录外部系统实际状态。

人工决定也被建模为一个明确节点。审批通过后才能进入外部动作，拒绝则不会留下模糊的“可能已执行”状态。

## 5. 可解释性是默认能力

每个重要判断都有对应投影：

| 你想知道什么 | 使用什么 |
|---|---|
| 当前目标是否稳定 | `hg status` |
| 为什么需要执行 | `hg plan`、`hg explain` |
| 哪些状态发生过变化 | `hg events` |
| 某个结果来自哪里 | `hg artifact history` |
| 某次执行发生了什么 | `hg logs` |

## 6. 把变化协调到固定点

一次 `hg run` 不只是启动一个 Rule。它会沿目标的输入闭包推进，直到目标新鲜、稳定，或明确报告阻塞、失败、取消和预算耗尽。

## 什么时候选择 HG-Rust？

HG-Rust 适合“输入变化会产生可检查结果”的工作，例如文档、报告、数据处理、评审、设计产物和受控的 Agent 任务。它不要求所有工作都由同一种执行器完成，也不把某个编程语言中的工作流函数作为唯一入口。

如果你的主要需求是定时触发云端任务、管理服务部署，或为长事务编写业务工作流，应该先阅读[与现有产品的对比](comparison.md)，再决定是否将 HG-Rust 放在系统中的结果协调层。
